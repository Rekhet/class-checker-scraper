Crawling & Data

Three SNU endpoints, each fresh on a different axis. The crawl merges them so the catalog is complete, the timing is as exact as available, and the volatile counts are as live as possible.

Timing: Excel overrides, search fills gaps

Timing is merged per class:

  • If the Excel has a time for a class → use the exact Excel blocks (start and end). Excel always wins.
  • If the Excel time is empty → fall back to search-cell timing.
  • If neither has a time → the class is 시간미정 (TBA) and carries no slots.

Rooms: one per meeting

The Excel 강의실(동-호) column lists one room per 수업교시 block, in the same / order (월(12:00~14:50)/화(11:00~12:15) ↔ 3-213/3-116), so each class_slots row carries the room that meeting uses (class_slots.room). A block repeated with two rooms means the class uses both at once and is stored as two rows; the UNIQUE key includes room for that reason. If the two columns ever disagree in length, a single distinct room still applies to every block, otherwise the room is '' (unknown), never guessed. Search-recovered timing has no room (''). classes.room keeps the deduplicated list (200-3220/200-1024).

Search, export, and lookup return one slot per meeting time, so a two-room meeting is still one time slot; its room joins both rooms with / (slots[].room in the exported JSON since 2026-10-09; '' = unknown). The cloud roster reseed sends DISTINCT day/start/end rows without a room: the collector never reads rooms. The cloud class_slots has had a room column (all '') since an accidental init_schema there on 2026-10-08.

Terms crawled before the room column existed were filled by scraper/backfill_rooms.py (see maintenance → room backfill); the Excel of every stored term back to 2020 still carries the column.

classes/rooms-index.json (exported with the full catalog) lists every room any stored meeting used, as [campus, building, name, last_year, last_term, terms_seen]. Names are normalized by scraper/rooms.py so one room is one key across terms: a leading # marks the 연건 campus and * 평창 (no prefix = 관악), and the 2020 terms and the 2021 여름학기 zero-pad each segment (001-101 = 1-101). The building is an inference from the name, used only for grouping and ordering. Observed 2026-10-09: 1,144 rooms (관악 1,094, 연건 39, 평창 11).

⚙️

The cell sweep is gated: it only runs for a term when the Excel has times for fewer than 50% of its classes (the timetable hasn't landed in the Excel yet — typically fall). Above that, the Excel-time-less classes are genuinely time-less (online / research) and never appear in cells, so sweeping would be pure waste. Tune with SEARCH_TIMING_MAX_RATIO.

How cell timing is built

A class that meets across several ½-hour cells is returned by several cell queries. Those cells are coalesced per day: contiguous 30-minute steps merge into a block, and a block's end is the last cell's start + 30 min. The result is approximate (±30 min on the end) but places the class on the right day and rough time — and is automatically replaced by the exact Excel time on the next refresh once SNU publishes it.

Counts overlay

Cart (장바구니신청) and enrolment (수강신청인원) move quickly and the Excel lags on them, so after the Excel/timing pass the crawl paginates the term's search roster and overlays only the count columns — identity, timing, professor, credits stay as the Excel wrote them. This pass can also be run on its own as a fast, frequent update between heavy Excel rebuilds.

평가방식 tagging (filtered Excel sweeps)

평가방식 (성적부여형태: A~F / S/U / S+/S/U) and 평가방식 전환가능여부 appear nowhere as columns — not in the Excel, not in the search-result items; only the per-class detail popup shows them. But both endpoints filter on them (srchMrksGvMthd / srchMrksApprMthdChgPosbYn), so refresh_grading() downloads the Excel once per filter value (3 + 1 downloads per term) and tags each class by set membership. The three 성적부여형태 codes partition the roster exactly, so coverage is 100%. Runs at the end of every crawl_term() (the rebuild wipes the tags with the rows) and stand-alone via crawl.py --grading-only for backfilling past semesters. The HTML search can't do this sweep — it is hard-capped at 10 rows per page.

인원 추이 collection windows

The 인원 추이 (enrolment-trend) chart is a time series: every counts pass records one count_passes row (the axis point, plus which of a=applied 신청, c=cart 장바구니, e=enrolled 수강인원 it collected) and appends a count_samples row only for the classes whose numbers actually moved — about 1% of the roster between two 10-minute passes. The export forward-fills from count_latest, so the published JSON looks exactly as it did when every class was written every pass; see the schema for why dense rows ran the cloud database out of write quota. Sampling is gated by collection windows in the project-root collect.env (local runtime configuration, sourced by refresh.sh and the server launcher) so the series only grows while the numbers actually move — outside every window no row is written and the chart stays dark. Each metric takes a list of windows (CART_WINDOWS, ENROLL_WINDOWS) checked by crawl.py:_in_windows(), because enrolment moves in several disjoint spans with long dead gaps between them.

Registration phase state-machine

Two independent cycles — a 예비 (preliminary) round in late July and the 본 (main) round in August — each run 장바구니 담기 → 전산확정 → 선착순수강신청; then two 개강전 변경 days, then the 개강후 정정 week. The two volatile columns never move together; 확정 days and the gaps between cycles move nothing. 2026-2학기 (from co010.action):

🧩

_in_windows() samples on ANY match, so the configured 담기 span and the four enrolment spans are captured while the 확정 days and the ~16-day 08-12~08-27 gap stay dark. The bounded enrollment timer further restricts the live 2026-08-07, 08-10, and 08-11 runs to 08:30–16:30. The bounded enrollment timer samples every five minutes from 08:30 through 09:00, then every ten minutes through 16:30. If a _WINDOWS var is unset the crawler falls back to the legacy single CART_START/END + ENROLL_START/END window (behaviour unchanged). The window arithmetic itself lives in scraper/windows.py, free of the crawler's Playwright import, so the publisher can ask the same question: python -m scraper.sync_counts warns (never fails) when a window is open but the newest sample is older than 45 minutes — 180 in a slow window — which is what a stalled cron-job.org dispatch looks like from this side.

Terms listed before their timetable

sugang lists a coming term well before its timetable. Sampled 2026-10-08 (2026 겨울학기, 2027 1학기): the Excel has every catalog column (교과목번호, 강좌번호, 이름, 학점, 학년, 개설대학·학과, 이수과정·교과구분, 정원, 강의언어, 개설상태, 비고) and 주담당교수 for 67–72% of classes; the 평가방식 filtered sweeps partition the roster exactly (A~F + S/U = total); the cc103 detail has 상대/절대평가 and professor e-mail but no 강의계획. 수업교시, 수업형태, and 강의실 are empty in the Excel and the search results, and every count is 0. Such terms are read on a GitHub runner by scraper/catalog_snapshot.py — the Excel and the 평가방식 sweeps only, never the search-timing sweep (it would page through the whole term and find no times) — and their classes export as 시간미정. See UPCOMING_TERMS in maintenance.

What a term refresh does

  1. Wipe only this (year, term) — other semesters stay intact.
  2. Download & parse the Excel → upsert every class with exact timing and each meeting's room.
  3. If Excel timing is largely missing, sweep the 168 search cells (concurrently) and attach coarse timing to the time-less classes.
  4. Paginate the search roster and overlay the selected live metrics.

.venv/bin/python scraper/crawl.py --collect catalog,enrollment,grading --years 2026 --terms U000200002U000300001

.venv/bin/python scraper/crawl.py --collect catalog,enrollment,grading --years 2026

# fast cart-only pass (no Excel, no cell sweep)
