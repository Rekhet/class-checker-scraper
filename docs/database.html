Database & Turso

One catalog, two interchangeable backends. Everything talks to the connection returned by db.connect(); switching SQLite ⇄ Turso/libSQL is a single environment variable and lives entirely in db.py.

The backend adapter

db.connect() resolves a backend from DB_BACKEND and returns a thin wrapper so the rest of the code is backend-blind:

  • Rows are normalised. SQLite rows support name access; libSQL returns bare tuples with no row_factory. The adapter wraps both so every row supports index and name access and is dict()-able — identical to sqlite3.Row.
  • One uniform connection exposes execute, executemany, executescript, commit, close, and sync over either driver.
  • Only db.py imports a driver. crawl.py and server.py never know which backend is live.
🔎

GET /api/status reports the active backend (sqlite or libsql), shown in the UI status bar as DB ….

terms & crawl_runs

terms(term PK, year, label) backs the semester selectors. crawl_runs(id, started_at, finished_at, status, message, terms, classes, slots) records each refresh for the status bar.

🧹

A refresh clears only the (year, term) catalogs it rebuilds (clear_terms) — refreshing one semester never wipes the others.

count_samples, count_passes & count_latest

The 인원 추이 history is stored as deltas. count_passes(year, term, ts, applied, cart, enrolled) records one row per collection pass — the chart's time axis, plus which metrics that pass looked at. count_samples receives a row only for the classes whose collected numbers actually changed; roughly 1% of a roster moves between two 10-minute passes. count_latest(year, term, sbjt_cd, lt_no, ts, …) is the materialised current value per class: the baseline a pass compares against and what the catalog overlay reads. All three are keyed by the STABLE class identity (year, term, sbjt_cd, lt_no), not classes.id, so the history survives the wipe+rebuild in refresh_all.

A sample row with every metric NULL is a tombstone: the class left the roster, so its series stops instead of being forward-filled forever. The export reconstructs each class's value at a pass as the newest sample at or before it, and leaves a metric the pass did not collect as null — a closed 장바구니 window must not draw a flat line through 수강신청.

📉

Storing every class every pass wrote ~1.25M rows a day and exhausted the cloud database's monthly write quota mid-semester on 2026-09-04, which stopped collection entirely. Delta storage is what keeps a full semester inside a small database — do not "simplify" it back to dense rows, and do not prune old samples: a deleted row is the baseline some later delta is relative to.

A catalog written before delta storage is migrated on the first connection: db.backfill_delta_tables() derives the axis and the baseline from the dense history and retires classes that had already vanished.

Migrating to Turso

Source is always the local SQLite file; destination is whatever db.connect() resolves from the environment. The copy is idempotent (each table is cleared then refilled, ids preserved for FK integrity).

# local Turso file (no daemon, no cloud)
DB_BACKEND=turso TURSO_DATABASE_URL=data/turso.db \
  .venv/bin/python scraper/migrate_to_turso.py

# remote Turso
DB_BACKEND=turso TURSO_DATABASE_URL=libsql://<db>-<org>.turso.io \
  TURSO_AUTH_TOKEN=<token> \
  .venv/bin/python scraper/migrate_to_turso.py

Then start the server with the same environment. The migration refuses to run if the destination resolves to SQLite, so it can't accidentally copy onto itself.

🔒

A libSQL file is single-writer like SQLite. Don't run a crawl (which writes) and serve from the same local file at the same instant — stop the server during a heavy rebuild, or point the server at a replica.
